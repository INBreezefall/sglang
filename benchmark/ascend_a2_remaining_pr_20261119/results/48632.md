# #48632 · Mooncake worker binding failures

Upstream main `1ed3e1d04b25ab007b4c80481b7b6e3a36836eb7` and the isolated candidate `77ba9f6f799f26e4ab0a43093d2a9dbd60f2ab4b` ran on the same hardware. Both revisions ran twice in main, candidate, candidate, main order.

The native NPU transfer-loop thread and its ThreadPoolExecutor initialized with either a valid local device or an out-of-range local device. Both sender poll entry points were then called. A real healthy NPU reduction checked the worker context. Network initialization and room state were controlled fixtures.

## Cross-host native transfer

Two physical hosts used separate NPU devices 1 and 2. Each arm ran two fresh endpoint pairs with eight 1 MiB destinations per pair. Ascend Direct 0.3.13.post1 verified 16/16 destination slices on main and 16/16 on the PR. The source recorded 2 and 2 native write calls respectively. The healthy transfer ran through the actual MooncakeKVManager executor and its foreground batch transfer. The source worker observed device IDs [1, 1] and [1, 1]. The room bootstrap was a fixture. To replay, run the probe on both hosts with CROSS_RANK set to 0 or 1, LOCAL_ADDR and PEER_ADDR set to their data-plane IPs, and the same RENDEZVOUS_PORT and CROSS_ROUND. Expose devices 0 through 7 and select the matching checkout and wheel on both hosts.
