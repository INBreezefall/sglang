# #48543 · Exact-size ACL host allocation

Upstream main `1ed3e1d04b25ab007b4c80481b7b6e3a36836eb7` and the isolated candidate `2877db5d3bf6b4e556f5a41d8e11576f7a947401` ran on the same hardware. Both revisions ran twice in main, candidate, candidate, main order.

Each process made nine allocations over three non-aligned byte sizes through the NPU host-pool entry point. The base used the torch allocator and the candidate used aclrtMallocHost. A surviving slice owned the memory during real H2D and D2H copies. Both arms verified returned bytes. Torch allocator counters cover allocations it owns. Direct ACL allocations are outside those counters.

## Full-sized GLM host allocations

Each process held all three BF16 target host mappings simultaneously at 49,280 tokens across 78 layers, 5,412,126,720 bytes in total. The latent K, rope and index K widths came from the checkpoint. Each of 2 hosts ran main, candidate, candidate, main. Nine surviving views covered the first, middle and final page/layer of each mapping and passed a device round trip. Allocation times are process medians; the DMA samples covered the nine selected views.
