# #48575 · Pinned allocator prewarming

Upstream main `1ed3e1d04b25ab007b4c80481b7b6e3a36836eb7` and the isolated candidate `d225360ab183cb679885e3433d0a631e578a8ab0` ran on the same hardware. Both revisions ran twice in main, candidate, candidate, main order.

Each new process used the same 64 MiB pinned segment reserve. The candidate ran the worker startup hook once. Nine real pinned allocations and H2D copies followed. Timings below isolate first-use latency and report the separate cost of moving work into startup.

| Startup prewarm hook p50 (ms) | 0.065 | 1.634 |

## Full-sized GLM host allocations

Each process held all three BF16 target host mappings simultaneously at 49,280 tokens across 78 layers, 5,412,126,720 bytes in total. The latent K, rope and index K widths came from the checkpoint. Each of 2 hosts ran main, candidate, candidate, main. Nine surviving views covered the first, middle and final page/layer of each mapping and passed a device round trip. Allocation times are process medians; the DMA samples covered the nine selected views.
