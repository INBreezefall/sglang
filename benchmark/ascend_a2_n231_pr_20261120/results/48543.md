# #48543 · Driver-requested pinned host memory

Compared upstream main `68c262b30617731b7e1761169aceb6b17feb918a` and the isolated PR `166bf929ff0e8c89bda2ef03ce98b162d1c5a664` on the same Ascend 910B4-1. Four fresh processes ran in main, PR, PR, main order per protocol. Both used the stock 64 MiB PyTorch pinned reserve setting and the production SGLang host-buffer entry point. Three simultaneous BF16 buffers used the complete GLM-5.2 pool geometry, with 78 layers, 128 tokens per page and widths of 512, 64 and 128. Each process created and destroyed three pools.

| Measurement | main | PR |
| --- | ---: | ---: |
| Logical payload at 385 pages | 5,412,126,720 B | 5,412,126,720 B |
| Host bytes requested from the driver with all three buffers live, 385 pages | 5,905,580,032 B | 5,412,126,720 B |
| Driver-requested bytes after dropping the last views | 5,905,580,032 B | 0 B |
| Driver-requested bytes at 397 pages | 5,905,580,032 B | 5,580,816,384 B |
| Outstanding bytes after an explicit PyTorch host-cache purge | 0 B | 0 B |
| Checked DMA round trips with only views retaining the allocations | 18/18 | 18/18 |
| First three-buffer allocation per fresh process, median of two | 29.06 ms | 37.44 ms |
| Repeated three-buffer allocations, median of four | 0.37 ms | 33.34 ms |

At 385 pages the PR requested 470.59 MiB fewer live bytes, a reduction of 8.36%. The default allocator reused the cached blocks quickly. The opt-in allocator paid for fresh allocations and released the requests as soon as their last tensor views disappeared. Both fresh runs on each arm reproduced the byte counts. These measurements establish an allocator footprint and lifetime tradeoff at a fixed model geometry. Whole-model serving throughput was outside this protocol.

**How the byte counts were measured.** `torch.npu.host_memory_stats()["allocated_bytes.current"]` reports active and cached pinned blocks owned by PyTorch, including rounding. For the PR, a counting wrapper forwarded the real `aclrtMallocHost` and `aclrtFreeHost` calls and included successful, outstanding requests. At the end of each PR process all nine direct allocations had nine matching successful frees. Each arm copied the same live page views to the NPU and back. A second protocol collected process RSS and allocation timings. Linux mapped these buffers into an 8 TiB driver address range and reported zero RSS for the particular mapping in both arms. The table reports allocator ownership. The registered CPU suite on the measured PR returned `5 passed, 2 subtests passed in 3.81s`.
